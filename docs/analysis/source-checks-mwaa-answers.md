## asset-triggering-and-conflation

# Non-partitioned asset scheduling semantics — Airflow 3.3.2 (main deltas noted)

Prefixes: `core/` = `.venv/lib/python3.12/site-packages/airflow/`; `sdk/` = `core/sdk/`; `main/` = `airflow-src/airflow-core/src/airflow/`; `main-sdk/` = `airflow-src/task-sdk/src/airflow/sdk/`.

## 1. When a DagRun is created (OR vs AND)

**Write side.** A task's success PATCH calls `register_asset_change` once per outlet payload (`core/models/taskinstance.py:1624-1663`). It inserts and flushes one `AssetEvent` (`core/assets/manager.py:350-352`), then `_queue_dagruns` (`:504-544`) upserts ADRQ rows for every unpaused consumer: Postgres `INSERT … ON CONFLICT DO NOTHING` (`:828-835`), other dialects savepoint+merge swallowing `IntegrityError` (`:809-825`). ADRQ PK is `(asset_id, target_dag_id)` (`core/models/asset.py:751-759`), so ADRQ is a **set of "asset X fired for dag Y" flags**, not an event queue; it is written in the same transaction that flips `ti.state` (`manager.py:539-541`).

**Read side.** Each loop: `_do_scheduling` → `_create_dagruns_for_dags` → `DagModel.dags_needing_dagruns` (`core/jobs/scheduler_job_runner.py:1922-1927, 2364-2381`). That loads *all* ADRQ rows (`core/models/dag.py:714-721`), builds `statuses={asset_key: True}` per dag from rows present (`:736-739`), and runs `AssetEvaluator` on the serialized `asset_condition` (`:754`). `SerializedAssetAny.agg_func=any`, `SerializedAssetAll.agg_func=all` (`core/serialization/definitions/assets.py:289,303`; `core/assets/evaluation.py:71-73`); an absent asset evaluates `False` (`evaluation.py:58-59`). **OR**: run when ≥1 of a1..a3 has a row. **AND**: only when all three do. Not-ready dags keep their rows (`dag.py:755-758` only `del`s local dicts).

**Creation** (`_create_dag_runs_asset_triggered`, `scheduler_job_runner.py:2554-2687`): lock all ADRQ rows for the dag (`:2574-2584`), `triggered_date=max(created_at)` (`:2593`), create one QUEUED `ASSET_TRIGGERED` run (`:2645-2657`), attach as `consumed_asset_events` every event on any scheduled asset/alias with `timestamp > coalesce(prev asset-run run_after, [min(DagScheduleAssetReference.created_at) if not catchup], date.min)` and `timestamp <= triggered_date` (`:2600-2643`), then **delete all locked ADRQ rows** (`:2672-2681`).

**5 events for a1 between loops → 1 run** (PK conflation). Caveat derived from code, not executed: `AssetEvent.timestamp` defaults at the flush on `manager.py:352`, the ADRQ `created_at` is written later at `:835`; events #2-#5 hit ON CONFLICT and leave `created_at` untouched, so their `timestamp > triggered_date` and they fall outside the window at `:2638`. They are not attached to this run and will surface in the *next* asset-triggered run's window (floor = this run's `run_after`). `triggering_asset_events` (`sdk/execution_time/task_runner.py:350-353`) therefore under-reports repeats. **Main differs structurally**: ADRQ PK becomes `(target_dag_id, asset_event_id)` (`main/models/asset.py:778-787`; insert `main/assets/manager.py:802-833`), consumption is `AssetEvent.id IN (queued ids)` minus already-consumed (`main/jobs/scheduler_job_runner.py:2799-2836`), `triggered_date=max(event.timestamp)` (`:2838`) — still 1 run, but all 5 consumed. Main also drops the `created_at` floor: with catchup off only queued events are consumed (`:2801-2818`).

**New event while a run is QUEUED/RUNNING → a second run is created** (the row was deleted at creation, so a fresh one is inserted) **unless** `count(QUEUED+RUNNING runs of the dag, any run_type) >= max_active_runs`, in which case the dag is removed from `triggered_date_by_dag` and its row is retained ("deferring", `dag.py:767-788`). So `max_active_runs` gates **creation** (count includes QUEUED) and, separately, queued→running in `_start_queued_dagruns`, which counts only RUNNING (`scheduler_job_runner.py:2722-2731, 2792-2805`; SQL pre-filter `core/models/dagrun.py:747-753`). Net: at the cap, further events conflate into the pending flag rows and release as one run when a slot frees. (`exceeds_max_non_backfill`, `dag.py:797`, is a further filter but is recomputed for asset runs only on finish, `scheduler_job_runner.py:2876-2881, 2940-2945`, never on asset-triggered creation.) Main: same gates (`main/models/dag.py:769-790`).

## 2. Does AND need a *new* event per asset since the last run?

Yes, with "last run" meaning **last asset-triggered run created**: the ADRQ row is the only memory, and all rows for the dag are deleted at creation (`:2672-2681`), not completion; nothing else deletes them except stale-dag cleanup (`dag.py:722-726`). Consequences: a manual/scheduled run does not reset the accumulator; in AND mode a1 firing 100× while a2 is silent stays one flag, and when a2 fires the single run's window captures every a1 event with `timestamp <= a2's created_at`. The docs sentence (`airflow-src/airflow-core/docs/authoring-and-scheduling/asset-scheduling.rst:78-79`) is accurate under that reading.

## 3. `inlet_events[asset]` in the Task SDK

`InletEventsAccessors.__getitem__` requires the asset to be in `task.inlets` (`KeyError` otherwise, `sdk/execution_time/context.py:1289-1291`) and returns an `InletEventsAccessor` with chainable `.after/.before/.ascending/.limit` (`:1170-1188`). `_asset_events` (cached) sends `GetAssetEventByAsset(name, uri, after, before, ascending, limit)` (`:1199-1213`; `sdk/execution_time/comms.py:1146-1153`) → supervisor → `client.asset_events.get` (`sdk/execution_time/supervisor.py:1862-1873`) → `GET /execution/asset-events/by-asset` (`sdk/api/client.py:881-884`) → `core/api_fastapi/execution_api/routes/asset_events.py:76-112`, which selects **all `AssetEvent` rows for that asset**, filtered only by timestamp bounds, ordered by timestamp, optional `LIMIT` (`:42-49`). **No run filter, no default limit, no pagination**; the whole result is materialised into a list and `[key]` indexes it (`context.py:1220, 1238-1239`). So `inlet_events[a2][-1]` yields a2's latest event even when a1 triggered the run; the cheap form is `.ascending(False).limit(1)[0]`. Each event exposes `source_dag_id/run_id/task_id/map_index`, `extra`, `partition_key`, `created_dagruns` (`core/api_fastapi/execution_api/datamodels/asset_event.py:42-56`). Contrast `triggering_asset_events`, built solely from `dag_run.consumed_asset_events` (`task_runner.py:350-353`). Main adds `.partition_key()`, `.partition_key_regexp_pattern()`, `.extra(k,v)` (`main-sdk/execution_time/context.py:1255-1270`; `main/api_fastapi/execution_api/routes/asset_events.py:114-148`), still `limit` only.

## 4. Echo / re-emit without a task

Yes. `POST /api/v2/assets/events` (`core/api_fastapi/core_api/routes/public/assets.py:366-405`) calls the same `register_asset_change(asset=asset_model, extra, partition_key, source_is_api=True)`; the event has all `source_*` NULL (`manager.py:337-348`), `extra["from_rest_api"]=True` is injected (`core/api_fastapi/core_api/datamodels/assets.py:216-219`), and consumers are queued identically. Cost per call: asset lookup + joined consumer load (`manager.py:317-325`), 1 `AssetEvent` insert+flush, 1 name/uri-ref `DagModel` select (`:387-400`), 1 batched ADRQ upsert, synchronous listener hooks in the API process (`:414-416`), `asset.updates` stat. Auth `requires_access_asset(method="POST")` (`:369`). It does not copy a prior event's `extra` — the caller resupplies it. `POST /assets/{id}/materialize` (`:408-480`) instead triggers the *producer* dag and creates no event. Main: same endpoint (`main/api_fastapi/core_api/routes/public/assets.py:404`).

## partition-key-mutex-and-duplicates

## Per-partition-key concurrency in the partitioned path (Airflow 3.3.2, main@73b07c5 noted where different)

Paths: `V` = `.venv/lib/python3.12/site-packages/airflow`, `M` = `airflow-src/airflow-core/src/airflow`.

### 1. No per-key mutual exclusion once the first run exists

`AssetManager._get_or_create_apdr` (`V/assets/manager.py:712-808`) runs inside the TI-success Execution API request (`V/api_fastapi/execution_api/routes/task_instances.py:670` → `V/models/taskinstance.py:1627`). It looks up only the newest APDR for the pair — `WHERE partition_key == target_key AND target_dag_id == dag.dag_id ORDER BY id DESC LIMIT 1` (`:751-758`) — and reuses it **only** `if latest_apdr and latest_apdr.created_dag_run_id is None:` (`:759`). Otherwise it inserts a fresh row with `created_dag_run_id=None` (`:791-798`). Nothing consults `dag_run.state`.

The scheduler side, `_create_dagruns_for_partitioned_asset_dags` (`V/jobs/scheduler_job_runner.py:2142-2361`), selects `created_dag_run_id IS NULL` (`:2178`) `ORDER BY created_at, id LIMIT 500 … FOR UPDATE SKIP LOCKED` (`:2181-2187`), evaluates the rollup, then `dag.create_dagrun(... partition_key=apdr.partition_key, run_after=timezone.utcnow(), state=DagRunState.QUEUED ...)` (`:2323-2347`) and stamps `apdr.created_dag_run_id = dag_run.id` (`:2356`). There is no query against existing `DagRun` rows for that key; the only dedup is the DAG-level, same-tick `partition_dag_ids` set (`:2367-2378`) that stops the cron/ADRQ paths from creating another run for the same *DAG* this tick. Consequence: key K fires → APDR#1 is closed → next event for K creates APDR#2 → when satisfied, DagRun#2 is created QUEUED while DagRun#1 is still QUEUED/RUNNING. The `asset_partition_dag_run` table has only the FK in `__table_args__` (`V/models/asset.py:946-953`), no unique on `(target_dag_id, partition_key)`.

The `_lock_asset_model` guard (`:71-129`) is per **producer `asset_id`**, rendered `FOR NO KEY UPDATE` (`V/utils/sqlalchemy.py:417-423` → `sqlalchemy/dialects/postgresql/base.py:2210-2211`), so it serialises same-asset writers only, not same-target-key writers.

**main:** `_get_or_create_apdr` is byte-identical (`M/assets/manager.py:705-801`). The scheduler function differs only by an added docstring and two predicates `DagModel.is_paused.is_(False), DagModel.is_draining.is_(False)` (`M/jobs/scheduler_job_runner.py:2385-2386`). No per-key gating in either tree.

### 2. #71070 / #71074

#71070 is a 3.3.0 bug report: two `asset_partition_dag_run` rows for the same mapped key created milliseconds apart (one with `partition_date` NULL), so the consumer never fired. #71074 ("Fix duplicate pending Dag runs for the same asset partition key") adds a `pending_partition_key` column mirrored while `created_dag_run_id IS NULL`, a unique constraint on `(target_dag_id, pending_partition_key)`, SAVEPOINT/`IntegrityError` handling in `_get_or_create_apdr`, and migration `0128_3_4_0_add_pending_partition_key_to_apdr.py`; milestone 3.4.0, still **open** (rebase requested 2026-09-26). Scope is **pending APDRs only** — the column is cleared when the run is created, so it deliberately does not constrain concurrent running runs. Tree check: `grep pending_partition_key` finds nothing in 3.3.2 or main; main's migrations already run to `0140` with `0128` taken by `add_asset_event_id_to_adrq.py`, consistent with the unmerged state. The failure mode matches the code: two *different* assets mapping to one target key are not serialised by the per-asset lock, so both take the insert branch and the `partition_date` reconciliation (`:759-790`) never runs — my inference, not a maintainer statement.

### 3. `max_active_runs` interaction and ordering

The cron path pre-gates creation via `dags_needing_dagruns` (`exceeds_max_non_backfill == false`, `V/models/dag.py:797`) and `_create_dag_runs` counts active runs (`:2437-2451`). The partition path bypasses both — no `max_active_runs` reference in `:2142-2361`; main's docstring says so verbatim (`M/...:2355-2357`). ## mapper-serialization-and-fingerprint

# Partition mappers with large / daily-changing reference data (Airflow 3.3.2; main 73b07c5 noted where it differs)

## 1. Serialization and where the mapper executes

The DAG author uses the SDK attrs classes; the SDK base (`sdk/definitions/partition_mappers/base.py:34-51`) has **no** `to_downstream`, `serialize` or `deserialize`. Those live on the core ABC (`airflow/partition_mappers/base.py:69-70, 141-148`); default `serialize()` emits only `max_downstream_keys` (`:141-144`).

`encode_partition_mapper` (`serialization/encoders.py:669-694`) maps a builtin SDK class to a core import path via `BUILTIN_PARTITION_MAPPERS` (`:444-458`) and a per-type encoder (`:461-540`); otherwise it takes `qualname(var)` and, unless it starts with `airflow.partition_mappers.` (`helpers.py:198-200`), calls `find_registered_custom_partition_mapper` (`helpers.py:143-150`), raising `PartitionMapperNotFound` (`helpers.py:184-195`) if the class is not in `AirflowPlugin.partition_mappers` (`plugins_manager.py:280-288`). The singledispatch fallback raises `NotImplementedError` unless the object is a *core* `PartitionMapper` (`encoders.py:461-465`), so a custom mapper must subclass the core ABC and be plugin-registered in the DAG processor, API server, triggerer and scheduler (shipped example: `example_dags/plugins/custom_partition_mapper.py:21,29,93`). Output is `{__type, __var}` stored under the timetable's `default_partition_mapper` / `partition_mapper_config` (`encoders.py:434-442`) in `serialized_dag.data`; decoding is `import_string`/plugin lookup then `cls.deserialize(var)` (`decoders.py:248-262`, `timetables/simple.py:413-424`).

`dag.partition_mapper_info` (`models/dag.py:410-412`, JSON NOT NULL) holds only `[{name?, uri?, is_rollup}]` (`timetables/base.py:46-60`, `simple.py:327-360`), written by the DAG processor (`dag_processing/collection.py:623`). It never contains the mapper.

`to_downstream` is called in exactly one place: `AssetManager._queue_partitioned_dags` (`assets/manager.py:605`). Its callers are `register_asset_changes_in_db` (`models/taskinstance.py:1558, 1625-1660`) invoked from the execution API `ti_update_state` (`execution_api/routes/task_instances.py:670`), the public `POST /assets/events` (`public/assets.py:391`), and `Trigger.submit_event` (`models/trigger.py:297`) from the triggerer (`triggerer_job_runner.py:768`). So `to_downstream` runs in the **API server** (or triggerer), never in the scheduler; the scheduler runs only `to_upstream`/`wait_policy` (`scheduler_job_runner.py:2046-2052`) and UI routes run `to_upstream` (`ui/partitioned_dag_runs.py:144,439`).

## 2. What is in `rollup_fingerprint`

`compute_rollup_fingerprint` (`timetables/base.py:523-567`) returns `{}` for non-partitioned timetables (`:542`), otherwise for every asset and asset-ref in `asset_condition` it stores `entries["{name}|{uri}"] = encode_partition_mapper(mapper)` (`:555, 561, 565`), i.e. the **full** serialized mapper including nested mappers/windows. The column is `AssetPartitionDagRun.rollup_fingerprint: JSON, nullable` (`models/asset.py:940`; migration `0121:55` `sa.JSON()`), no size limit in the schema. Despite the name it is stamped on every partitioned consumer's APDR, not just rollups (`manager.py:597, 697, 796`). For `AllowedKeyMapper` the encoder writes `{"allowed_keys": partition_mapper.allowed_keys}` (`encoders.py:525`), so a 10k list is copied into every APDR row and re-serialized per event per consumer (`manager.py:597`). For a custom mapper only what its `serialize()` returns is stored; a 10k dict kept out of `serialize()` stays out of the fingerprint, but then changes to it neither survive deserialization nor invalidate pending APDRs, which is the ambiguity to decide deliberately.

## 3. Fingerprint mismatch on re-parse

In `_create_dagruns_for_partitioned_asset_dags` (`scheduler_job_runner.py:2142`), each tick loads up to `_max_partition_dag_runs_per_loop` pending APDRs (`:2174-2189`), recomputes the fingerprint from the latest serialized DAG (`:2215-2222`; a failure, e.g. missing plugin, skips that DAG), and marks stale any APDR whose stored value is `None` or `!=` the latest (`:2229-2230`). Stale APDRs and their `PartitionedAssetKeyLog` rows are bulk-deleted in the same transaction (`:2245-2250`) with an INFO log (`:2237-2244`). Nothing re-queues the consumed events: a rollup window that was 6/7 complete loses its progress; an identity consumer only loses events that arrived between the re-parse and the tick. With a daily-regenerated `allowed_keys` list, every daily parse wipes all pending APDRs for that DAG. Main is byte-identical here (`airflow-src/.../scheduler_job_runner.py:2409-2468`) and in `manager.py` (`:590, 598, 690`).

## 4. I/O in mappers: guards and cost

There is no timeout, sandbox or documentation constraint; docs (`assets.rst:1144-1160`) cover only plugin registration. `to_downstream` is wrapped in a bare `except Exception` that writes a `Log(event="failed to map partition_key")` and `continue`s (`manager.py:603-628`); `to_upstream` failures in the scheduler return "not satisfied" and are retried every tick (`:2064-2074`). The call runs inside the execution API's transaction, which already holds `SELECT ... FOR UPDATE` on the TI (`task_instances.py:641`), so mapper latency extends the row lock and the HTTP request. Per event per partitioned consumer the API server does `SerializedDagModel.get` (`manager.py:590`), full DAG deserialization (`:593`; `serialized_dag.py:902-911` is an uncached property), `compute_rollup_fingerprint` (`:597`), an `AssetModel` select (`:599`), `to_downstream` (`:605`), then per target key an asset-row lock plus select/insert (`:773-797`). `add_partitions` with N keys yields N `register_asset_change` calls in one request (`taskinstance.py:1625-1660`). The only cap is on fan-out count, `max_downstream_keys` / `[scheduler] partition_mapper_max_downstream_keys` default 1000 (`manager.py:584, 635-668`; `config.yml` under that key), not on time or I/O.

## 5. `AllowedKeyMapper` / `FixedKeyMapper`

SDK `AllowedKeyMapper.allowed_keys: list[str]` (`sdk/.../allowed_key.py:28`); core stores the list and does an O(n) `key not in self.allowed_keys` (`partition_mappers/allowed_key.py:30-35`) and serializes it whole (`:37-41`). It lives in the DAG file, `serialized_dag.data`, and every APDR fingerprint; no explicit limit beyond JSON column sizes. `FixedKeyMapper` holds one `downstream_key` str (`fixed_key.py:46-58`); its key set is the paired `SegmentWindow`, also serialized into the fingerprint via `encode_window` (`encoders.py:534`). Partition keys themselves are capped at 250 chars (`sdk/execution_time/context.py:1034-1036`).

## Recommendation for daily-changing region->account maps

Keep mappers static (`IdentityMapper`) and resolve the map where retries, timeouts and workers exist: (a) the producer task reads the mapping and calls `outlet_events[asset].add_partitions([...accounts])` (`context.py:1038-1061`), bounding keys per task since each key costs the per-event work above; or (b) a small router DAG consuming the region asset (identity) whose task emits account keys to a second asset. Do not use `AllowedKeyMapper` for validation at this size: it makes the fingerprint change daily and wipes pending APDRs.

## Conclusion

Serving tens-to-hundreds of concurrent end users from Airflow's REST API is not advisable: every list page costs a COUNT, partition filters are unindexed substring/range scans over `dag_run`, the state-store cannot be enumerated efficiently, and (unless `--apps` is split) user traffic competes with task heartbeats and state updates in one process. Cheapest correct projection: a DagRun listener plugin on the scheduler (`on_dag_run_running/success/failed`) that enqueues `(dag_id, partition_key, state, end_date)` non-blockingly to your own store keyed by `(dag_id, partition_key)`, plus a single reconciliation poller using cursor-mode `GET /dags/{id}/dagRuns` with `updated_at` bounds (`dag_run.py:655-660`) to repair swallowed listener errors. Use `asset_state_store` only for per-key point writes the task itself needs to read back.

## 1. What `@asset` generates

`asset.__call__` builds an `AssetDefinition(name=self.name or f.__name__, uri=name if uri is None ...)` (`sdk/definitions/asset/decorators.py:230-241`). `AssetDefinition` **is an `Asset`** (`:119`); its post-init does `with self._source.create_dag(default_dag_id=self.name): _instantiate_task(self)` (`:129-131`). `create_dag` returns `DAG(dag_id=self.dag_id or default_dag_id, schedule=self.schedule, catchup=False, ..., auto_register=True)` (`:186-204`), so **dag_id == asset name** unless `dag_id=` is given, and `schedule` is a *required* attribute (`:171`, no default). The single task is `_AssetMainOperator(PythonOperator)` with `task_id=f.__name__`, `outlets=[the asset]`, and `inlets=[Asset.ref(name=p) for every non-defaulted param not in ("self","context","outlet_events")]` (`:63-74`). Stacking `@asset` over `@task.*` is allowed: `_instantiate_task` injects `outlets` into the decorator kwargs and raises if the user already set them (`:106-115`).

**Partitioned schedule:** `ScheduleArg = Union[ScheduleInterval, BaseTimetable, CoreTimetable, BaseAsset, Collection[BaseAsset]]` (`sdk/definitions/dag.py:107`); the SDK `PartitionedAssetTimetable` is a `BaseTimetable` (`sdk/definitions/timetables/assets.py:36,49`) and passes through `_default_timetable` unchanged (`dag.py:669-670`), then serializes to `airflow.timetables.simple.PartitionedAssetTimetable` (`core/serialization/encoders.py:333,434-442`). Nothing blocks `@asset(schedule=PartitionedAssetTimetable(...))`, but the docs never show it: every `PartitionedAssetTimetable` example is `with DAG(dag_id=...)` (`assets.rst:597-599,656-658,787-789`), while `@asset` is only paired with `PartitionedAtRuntime()` + `outlet_events[self].add_partitions(...)` (`assets.rst:968-973,984-989`). Treat `@asset`+`PartitionedAssetTimetable` as type-legal but undocumented/untested.

**Emitting keys:** the reserved `outlet_events` param is `context["outlet_events"]`, `self` is the Asset fetched via `GetAssetByName` (`decorators.py:92-97`). `add_partitions(str|list)` validates non-empty, ≤250 chars, rejects aliases (`sdk/execution_time/context.py:1038-1062`); the runner emits one event dict per key, all sharing one `extra` (`task_runner.py:1390-1400`) — no per-key `extra`.

**Chaining:** function parameters become **inlets, not a schedule** (`:65-70`); the docs' chained example still uses `schedule=None` (`assets.rst:309-311`). To make asset B run on asset A, pass A's `AssetDefinition` as `schedule=`: `isinstance(schedule, BaseAsset) → AssetTriggeredTimetable(schedule)`, a collection → `AssetAll(*schedule)` (`dag.py:671-678`).

**Intended granularity:** docs call `@asset` the shorthand for "creating a Dag with one single task that emits events of one asset" (`assets.rst:174,185-189`); `asset.multi` docstring: "Create a one-task Dag that emits multiple assets" (`decorators.py:219`). ## 2. Multi-task DAG (gate → batch → emit) with outlets on the last task

Identical persistence path: `_handle_current_task_success` builds `SucceedTask(task_outlets, outlet_events)` (`task_runner.py:1764-1778`) → `TI.register_asset_changes_in_db` (`core/api_fastapi/execution_api/routes/task_instances.py:668-675`) → one `AssetEvent` per key with `source_task_id/source_dag_id/source_run_id/source_map_index` (`core/assets/manager.py:344-347`). Nothing `@asset`-specific is stored (`_AssetMainOperator` keeps only `_definition_name`, `:58`). The asset graph is built from `task.outlets` and schedule refs only — inlets produce no edges (`core/serialization/serialized_objects.py:942-954`). So lineage/UI are the same; only DAG shape differs. Two gotchas: a successful outlet task that added **zero** keys still emits one event with `partition_key=dag_run.partition_key` (`core/models/taskinstance.py:1625-1636`), which partitioned consumers reject with a "missing partition key" `Log` row (`manager.py:558-582`); and each event fans out via `mapper.to_downstream` into `AssetPartitionDagRun` + `PartitionedAssetKeyLog(asset_event_id=event.id, source_partition_key, target_partition_key)` rows (`manager.py:692-709`) under the `max_downstream_keys` cap (`:584,645-669`), which for `IdentityMapper` is 1 key/event and never trips.

## 3. Skip semantics

`AirflowSkipException` → `TaskState(state=SKIPPED)` with **no outlet payload** (`task_runner.py:1619-1628`); the server calls `register_asset_changes_in_db` only for `TISuccessStatePayload` (`routes/task_instances.py:668-675`); `TITerminalStatePayload` (SKIPPED/FAILED) never reaches it. main is identical (`main: task_runner.py:1645-1654`, `routes:743-745`).

`ShortCircuitOperator` does **not** skip itself: on a falsy condition it returns `condition` and succeeds (`providers/standard/operators/python.py:352-358,392-394`), skipping downstream via `SkipMixin.skip` → bulk `UPDATE ... state=SKIPPED` (`sdk/bases/skipmixin.py:58-82`; `routes:853-863`). Downstream tasks never run, so their outlets never register — correct for gate→batch→emit. But outlets placed **on the gate itself** emit even when it short-circuits. Worst case: `@asset` over `@task.short_circuit` (`_ShortCircuitDecoratedOperator`, `decorators/short_circuit.py:30-60`) — with no downstream tasks it hits `if not self.downstream_task_ids: return condition` (`:356-358`), succeeds, and emits an event with no key. Inside a 1-task asset the only suppressor is raising `AirflowSkipException`.

## 4. Downstream visibility and per-key lineage

The scheduler creates the consumer run with `partition_key=apdr.partition_key` and extends `consumed_asset_events` with **only** the events whose `PartitionedAssetKeyLog` rows map to that APDR (`core/jobs/scheduler_job_runner.py:2333-2354`) — not all 500. In the task, `triggering_asset_events` is built from `dag_run.consumed_asset_events` (`task_runner.py:350-352`), each `AssetEventDagRunReference` carrying `source_task_id/source_dag_id/source_run_id/source_map_index/partition_key/extra/timestamp` (`sdk/api/datamodels/_generated.py:712-728`). Per-account lineage therefore resolves to (producer run_id, emitting task_id, map_index) + `partition_key`; all 500 events from one TI share the same source triple, the key is the only discriminator.

UI/API in 3.3.2: `GET /dags/{dag_id}/dagRuns/{run_id}/upstreamAssetEvents` returns consumed events (`core_api/routes/public/dag_run.py:265-300`); `GET /assets/events?partition_key=` exact/pattern filters (`routes/public/assets.py:474`, `datamodels/assets.py:212`); UI endpoints `/ui/partitioned_dag_runs` and `/ui/pending_partitioned_dag_run/{dag_id}?partition_key=` return per-key `total_received/total_required` (`routes/ui/partitioned_dag_runs.py:242-253,352-360`; `datamodels/ui/partitioned_dag_runs.py:22-32`). The shipped bundle has `partitionKey`, `mappedPartitionKey`, `partitionedDagRun*` labels (`ui/dist/i18n/locales/en/common.json:75-77,196-198`) and the event card renders `partition_key` (minified `index-1ifPC3Lo.js`; unciteable by line). The dependency graph (`routes/ui/dependencies.py:50-81`) is static per asset node — there is **no per-key graph view** in 3.3.2 or main.
