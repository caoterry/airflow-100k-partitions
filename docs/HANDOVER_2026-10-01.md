## Lessons / catches

- A sentence written from memory into a public PR body ("~3×") was contradicted by our own committed data within a day; every number
  in a public body must point at a committed file. Two more report numbers (§4.1, §4.6) had the same problem; one was recoverable from
  the bench DB, one was not and is now marked as such.
- Two sessions on one branch: the second one pushed from stale context and undid a verified fix. Ownership must be explicit.
- On MySQL, InnoDB retires its implicit FK index when a composite starting with the same column is created, with or without dropping
  the constraint first; the upgrade-side FK dance was a no-op that forced a table copy. Precedent for the pattern is migration 0122.
- pymysql needs `?client_flag=65536` (MULTI_STATEMENTS) for Airflow's MySQL migrations; MySQL's docker image restarts once during init
  (wait for "ready for connections … port: 3306", not for the temporary server).
- From `~/Code/airflow-fork`, docker needs `--context colima` (no `/var/run/docker.sock`).
- `grep -c` returns exit 1 on zero matches and silently breaks `&&` chains; two scripts were lost that way.
- Teaching: a fill-in-the-blank only works on a mechanism already walked through; otherwise multiple choice.

## Today's meeting: cheat sheet (Terry listens; ~10 minutes of questions)

Opening, one sentence: *I spent two days measuring where Airflow actually breaks for this: one run per account at 100k is the only
hard limit; your region/pack split with per-account observability works on MWAA as shipped. I mostly want to hear your plan and
check a few things against the numbers.*

Four questions, each asked when the colleague reaches the topic, no position needed:

1. On end-user tracking: *Do users only need to see an account's status and version, or re-run it themselves?* (see-only → Shape 2 on
   MWAA is the whole recommendation; self-service re-run → Shape 1, which MWAA cannot run until the index ships).
2. On Phase 1 / planes: *Which part do you want to lock in: the declarations, or the runner underneath?* (declarations → Airflow can be
   one compile target for them; runner → our work becomes the "Airflow scaling boundaries" evidence and the Airflow track parks).
3. On the platform catalog: *Is MWAA the only Airflow route we have, or is there a Kubernetes offering?* (factual check; "only MWAA"
   confirms the hard constraint; follow-up: *by when must Phase 1 run?*).
4. On "is fine-grained scheduling really needed" / the 38-minute footnote: *Is the 2-minute p95 for the intraday trickle only, or the
   burst too? And roughly what are engine start-up and max concurrency?* (S and K are homework; with them the simulator answers the
   grain question the same day).

The conditional batching answer, if asked: *If engine start-up is around ten seconds, SLA-driven batch sizing meets a 2-minute p95 in
simulation (4.9 job-hours vs 11.6 for latency-optimal); at sixty seconds nothing does. So I need your numbers for start-up and
concurrency before I can say more.* Closing: *I'll write up what I heard against the measurements and send it tomorrow.*

The frame for comparing whatever is presented (five dials; the colleague's Option A differs on signal, batching, state and rerun,
and shares the grain; his Proposal MVP sits on nearly the same dials as ours, the difference is who executes them):

| dial | ours |
|---|---|
| signal (how arrivals are known) | asset events emitted by producers, not sensors polling the data platform |
| decision (edge vs level) | level: a cron/continuous `claim` reconciles a persistent ledger (`seen_version > done_version`); events are the log |
| scheduling unit | one dynamic batch (never one account; balance sheet: one business date) |
| batch sizing | `b_sla = (target − S) / (1/λ + p)`, floored by capacity, clamped; pool = K |
| state | off the run graph: asset state store (current) + ledger (pending / inflight / done) + keyed events (lineage) |
| rerun | revenue: ledger re-opens on a newer version, repair entry by account list; balance sheet: OR trigger + gate `all(reference) and any(root)` per date, whole recompute |

What to admit if asked: nothing has run on MWAA itself (3.3.2 locally; MWAA constraints are from AWS docs); the Execution API in
MWAA's webserver containers is the one untested spot (that is where the ~5 ms/key registration lands); `spark` was a sleep; the
100k batcher reached 84k in the window; E7 not built; Dagster not evaluated; the public repo has internal names and wording removed
and can be made private on request. Open-source coordination: #73983 is indexes only; the "rerun enhancement we contribute" cell on
the matrix can be retired (OR + version gate needs no core change); the firm's upstream effort, if any, belongs on per-key
concurrency / conflation and batched key registration.
