Can Airflow orchestrate 100,000 partitions?

First the jobs an orchestrator does, and how native Airflow does them. Then what happens at 100,000 partitions, split into two separate problems. Then one route, what it did at 100,000 partitions, and what is still open.

2 · The orchestrator's jobs

What an orchestrator does, and how Airflow does it

Whatever grain the calculation team picks, an orchestrator does the same jobs. In Airflow each job hangs on runs, tasks and events. With native asset partitions, the partition is the unit for all of them.

Natively, each partition is a run, with its own task instances and events. That is why retry, rerun and lineage per partition come out of the box. The next question is what that means when there are 100,000 of them.

RetryRetry a failed piece of workTask instance retries. One partition per run, so retries are per partition.

RerunRun a piece of work again on demandClear a run, or trigger a run for one key.
LineageRecord which inputs produced each resultAsset events attached to each run.
3 · Two separate problems

Can Airflow track 100,000 things? And how many engine jobs run?

These are different questions with different fixes. The first decides whether Airflow can be the orchestrator at all. The second is about the engine, and it stays open.

Problem 1 · Orchestration

Airflow's cost grows with the number of objects it tracks

  • Every object is rows: a run, a task, an event, a queue entry.
  • One Python loop in the scheduler looks at those rows, at least twice per run.
  • Some steps touch all of them at once, inside one transaction.
  • So the count breaks it. Data size only costs time.
Problem 2 · Compute

How many engine jobs, and how big

  • A Spark job pays start-up per job. One job per partition pays it 100,000 times.
  • Lambda per partition might work, if the fan-out stays inside one task. Not measured.
  • Whatever the engine, problem 1 stays the same.
  • No real engine ran in any test here.

Where the 100,000 go: three native ways to schedule them

    Measured in earlier runs in the same local environment, recorded in the repo report. The first way also writes 100,000 rows into each of seven tables, again at every downstream hop. MWAA can run more schedulers, but gives no database access to add the indexes.

    That leaves one question. Can Airflow keep its object count small, like batching, and still know per partition what changed and what is done?

    5 · Deep dives

    Deep dives

    Each tab takes one design question: how it works on this route, what we measured, and what is still open.

    The questionWhat does 100,000 partitions cost Airflow on this route, and where will it break first?

    Airflow objects do not grow with partitions: one landing is 6 events, 6 runs, 25 task instances, against 100,000 native runs. What grows is the size of the partition lists we store, and we plan to split those into small keys.

    How it works

    • Partitions travel as data inside the landing event, the window key and the batch key. Airflow schedules windows and batches, never partitions.
    • One landing costs six runs: debounce, batcher, an empty batcher tick run, ledger, and two runs of the example downstream Dag.
    • What grows with partitions and inputs is JSON size. Each state-store get or set, or XCom push or pull, of 4.4 to 5.5 MB took 1.9 to 3.8 s. One run made about 15 of them in series.
    • The journal and the partition lists are split by partition into keys under the state store's 64 KB limit, for example 128 keys. A small batch then rewrites only the keys it touches. Planned, not built.

    Measured

    Airflow objects, one 100,000-partition landing6 asset events, 6 Dag runs and 25 task instances, counting one unexpanded Spark placeholder. In the stream run, 200 landings of 500 partitions made 315 events and 139 runs. Native asset partitions: 100,000 rows in each of seven tables per hop.
    Where the 93 s went (measured once, local environment, not MWAA)15 s designed waits (10 s window, 5 s ledger margin), 26 s engine stand-in, 52 s Airflow work. About 40 s of the 52 s went on moving 4.4 to 5.5 MB JSON values. About 13 s was XCom pulls; passing keys instead would likely remove them, not tried. The scheduler never lagged more than 0.6 s. Real Spark time is not measured.
    Value sizes, and the splitToday the journal is one key: 4.4 MB with one input, 7.2 MB with two. Split into 128 keys, each is about 34 to 56 KB.

    Where the 93 seconds of one landing went

    About 40 of the 52 seconds of Airflow work was moving these multi-MB values. Passing the batch key instead of the batch would likely cut about 13 seconds of XCom; not tried yet. Real Spark replaces the 26-second stand-in.

    The questionWhen big jobs hold every lane, how long does an adjustment wait, and can you keep p95 under 2 minutes?

    With lanes free, every landing was done within 60 seconds; with all three lanes busy, the last 48 landings waited 308 to 378 s behind one merged job. A reserved pool for small landings would keep an adjustment off that queue: designed, not built.

    How it works

    • A landing waits out its debounce window, then rides one v2_batcher run. Up to K = 3 runs overlap (max_active_runs) and share the 3-slot v2_spark pool.
    • In the prototype, with all 3 runs busy, windows queue in Airflow and the next free run takes them together. Its claim makes one Spark job per run, with no size cap. Runs also hold their lane, though not a pool slot, during claim, publish and finalize: for 73.8 s in total a window was waiting while fewer than 3 Spark tasks ran.
    • The design: small landings are routed before merging, through their own window, to a reserved small pool. The batcher's max_active_runs sits above the large slots, so a small run can always start. Large merged work is capped and split across free lanes. Designed, not built.
    • Window length trades fewer jobs for longer waits. Under load the queue merged windows anyway, so a long window buys little there. The proposed 60 s window adds up to 50 s: about 110 s worst case with lanes free; arithmetic, not measured. Real Spark would take longer than the stand-in's 7 s sleep.

    Measured

    Neither run used real Spark. They test how batching behaves at two engine speeds, not how fast Spark is.

    The questionIf positions and trades for one account land seconds apart, which versions does the final PnL use?

    The newest of both, under a rule that is designed, not built: each job reads the newest version of every input when it starts and reports that set, and a result older on any input is rejected.

    The questionFor any one of 100,000 accounts, where do I see its status, why it failed and which inputs it used?

    Partly: each batch is a run that turns red when partitions fail, and the journal holds each partition's state and versions. An operator reads it as raw JSON today: no per-partition view is built, and waiting partitions are not tracked.

    How it works

    • Airflow shows the batch. Each batcher run is one Dag run; its check task turns it red when partitions go to failed. If a job dies before publish, its partitions ride once more and that run stays green.
    • The journal shows the partition. In the asset state store on v2_pnl, done and failed map each partition to its input versions. Each batch/<run_id>#<i> key holds its state (claimed, running, done, failed), versions, culprits and the error's first 300 characters. The asset's State Store tab lists them as raw JSON, each linked to the task that last wrote it.
    • Lineage is a chain: landing events, window key, batch key, v2_pnl event, downstream run. Airflow records which events each run consumed, and each batch key carries its batcher run id.
    • Proposed, not built: a status task at the end of v2_ledger, the only writer of done and failed. It writes a summary key under 64 KB, readable on the tab. It upserts one status row per folded partition: state, versions, batch key, error. Joined with the output table, the rows show whether each result was written.

    Measured

    What Airflow shows for one 100,000-partition landingLocal environment, not MWAA. 6 Dag runs, all succeeded, and 6 asset events. Sizes: landing 2,400,077 bytes, debounced 139, PnL 130, finished 79, two ticks of 14 bytes.

That is 67 times the 64 KB policy default; with two inputs, done reached 7,200,000 bytes. Task writes above it only warn; REST writes, including edits from the tab, are rejected.           The questionIf one account comes out wrong, or we need to recompute a whole set, how do I rerun just that?

          A failed partition can be re-queued with one call, and changed input recomputes a partition by itself. Forcing a done partition to recompute, and backfilling a list or a date, are not built yet.

          How it works

          • Built: v2_requeue rings one event on v2_inputs_debounced for listed partitions that are in failed, with the versions they failed on. It skips the debounce window, and claim runs them in their own quarantine job. It still waits for a free batcher run.
          • Built: a producer landing with a newer version and a changed marker recomputes that partition, failed or done. For a done partition, the same version or an unchanged marker recomputes nothing.
          • To build: v2_recompute takes a list or a selector, such as all done partitions or those landed on a date. It writes the list to one state-store key, rerun/<run_id>, and rings one pointer event with force set.
          • To build: claim lets a forced partition ride even when the due rule says no; failed ones still go to quarantine. Recomputing a past business date with that day's inputs needs the date in the key; not designed.

          The questionIf one account breaks the Spark job, do the other 99,999 fail with it?

          Airflow retries first; after the last try, only partitions the engine names go to failed, and the rest ride once more. Tested on six partitions locally, never at 100k; if the engine names nobody, the whole batch fails.

          How it works

          • Airflow retries first: spark gets one retry 5 s later, claim and publish get two. Our code records no verdict before the last try.
          • After the last try, spark marks its batch key failed. Partitions the engine error names go to failed; ring_retry rings the rest once. A retry batch never isolates again. If the error names none, the whole batch fails.
          • A job that ended without publishing is re-rung once, then failed. v2_ledger alone writes failed; check then turns the run red. Failed partitions later ride in their own quarantine job on newer input, or when an operator lists them in v2_requeue.
          • Risks: culprits are partition names found in the error text, so the calc must name them; ACC1 also matches ACC12. A Spark outage outlasting one 5 s retry puts the whole batch in failed until newer input or a re-queue. With several inputs, another input's landing can clear a failure without computing it (the multi-input case of deep dive 3).
