# Research sweep digest (2026-09-29)

Six independent researchers with web access; each key claim fact-checked by a separate skeptic agent (verdicts inline). Raw JSON: `research-sweep-2026-09-29.json`.


## dagster-gap: What "partitions" means in Dagster, Dagster's own scale limits at 30k–100k keys, and the precise semantic gap versus Airflow 3.2/3.3 asset partitions (AIP-76), including what is emulable today

Dagster fit. "One partition per firm account, 30k–100k keys" maps to DynamicPartitionsDefinition(name=...): keys live in the instance database and are added/removed via instance.add_dynamic_partitions / delete_dynamic_partition or SensorResult(dynamic_partitions_requests=...). StaticPartitionsDefinition would need a redeploy per account change and historically hit O(N) scans (issue #12441: 90k multi-partitions timed out the 60s user-code-server call in 1.1.18, fixed by PR #12431). MultiPartitionsDefinition (date x account) is ruled out by arithmetic: Dagster's guidance is "limit the number of partitions for each asset to 100,000 or fewer" (docs 1.13.24, and the same sentence on the API page for Static/Dynamic/Multi), so 100k accounts x even one day already exceeds it; maintainers told a 200 clients x 1,000 days (200k) user to split clients into stable groups of separate assets (discussion #18788).

Is 100k comfortable in Dagster? No. The guidance was 25,000 until 2025-04-11, when Dagster staff (Gareth Brickman, discussion #21581) raised it to "100k in OSS and 250k in Dagster+"; the stated reason is only UI load time ("synced/unsynced status and reporting the materialization status of each partition", Jamie DeMaria). Field reports show other subsystems degrade earlier: 33,662 partitions made the partitions tab take >90s (issue #10330, 1.0.12); >40k froze Dagit (issue #15679); a ~50k-partition backfill stalled the backfill daemon at ~30 iterations/s, ~9,000 partitions per 5 minutes (issue #15241, 1.3.13); ~15,000 partitions caused automation-condition sensor DB statement timeouts (issue #31990, 1.11.5, closed not-planned); a fix for a 30s+ partition-selector freeze at "100k+" shipped in 1.12.14. High-cardinality users are told to batch keys, split assets, or run retention sensors that delete dynamic partition keys (data-retention page); the partitions-vs-config page says parameters from "an unbounded set" belong in run config, not partitions.

What Dagster partitions buy that Airflow lacks: (a) a partition catalog (registered key set) with per-partition materialized/missing/failed status; (b) partition-subset backfills by arbitrary key selection, with BackfillPolicy.single_run / multi_run(max_partitions_per_run) and partition_key_range in context; (c) PartitionMapping classes (Identity, TimeWindow with offsets, Static, All, Last, Multi) driving both dependency resolution and status; (d) AutomationCondition.on_missing/eager evaluated per partition; (e) partitioned IO managers; (f) report_runless_asset_event to mark partitions materialized externally.

Airflow today (3.2.0 released 2026-04-07; 3.3.0 2026-07-06; 3.3.2 2026-09-17; MWAA supports 3.3.1 since 2026-09-01). partition_key is a string column on dag_run and asset_event (3.2.0). Producers: CronPartitionTimetable (date keys, key_format default '%Y-%m-%dT%H:%M:%S') or PartitionedAtRuntime + outlet_events[asset].add_partitions("acct-123" | [list]) (3.3.0). Consumers: PartitionedAssetTimetable with mappers (Identity, StartOf*, Product, AllowedKeyMapper, FixedKeyMapper; 3.3.0 adds RollupMapper/FanOutMapper/SegmentWindow/wait_policy WaitForAll|MinimumCount). The scheduler tracks pending consumer runs per key in an AssetPartitionDagRun table (PR #71074). Fan-out per upstream event is capped by [scheduler] partition_mapper_max_downstream_keys, default 1000. Per issue #67368 (3.3.0 milestone), DagRun.partition_key is "provenance" and AssetEvent.partition_key is a "routing pointer"; there is no registered key set, no per-key status view beyond the next-run-assets partial-window progress, and backfill accepts only --from-date/--to-date interpreted as partition dates (AIP-76: "Only assets with time-based partitioning can be backfilled").

Emulable now: per-key run history (dag_run.partition_key + REST filters), per-key metadata via asset-event extra (JSON), AssetAlias to resolve concrete assets at runtime, a ledger table via AIP-103 asset_state_store (3.3.0) or an external table, categorical rollups via RollupMapper+SegmentWindow for small fixed sets. Not emulable without upstream work: a partition catalog with status, key-subset backfills, single-run backfill policy, partition-status-aware automation, and any tested path to 100k pending partition rows.

**Config knobs**

- [scheduler] partition_mapper_max_downstream_keys — default 1000 (added 3.3.0). Caps how many downstream partitioned Dag runs one upstream asset event may create; when exceeded the runs are not queued and an audit-log 'partition fan-out exceeded' entry is written. Overridable per FanOutMapper via max_downstream_keys/max_fan_out. Env: AIRFLOW__SCHEDULER__PARTITION_MAPPER_MAX_DOWNSTREAM_KEYS.
- [core] max_active_runs_per_dag — default 16. Bounds concurrently active runs per Dag; 100k per-account partitioned runs of one consumer Dag would drain through this window (can be raised per Dag).
- [core] parallelism — default 32. Max concurrently running task instances per scheduler; an upper bound on per-account task throughput regardless of partition design.
- [core] max_map_length — default 1024 (added 2.3.0). Caps dynamic task mapping fan-out; rules out 'one mapped task per account' inside a single run without batching.
- [api] maximum_page_limit — default 100. Caps REST page size when listing dag runs / asset events by partition_key for a status ledger.
- [workers] state_store_backend — added 3.3.0 (AIP-103). Selects the backend for task_state_store/asset_state_store (metadata DB by default); candidate home for a per-account processed/stale ledger.
- [core] rerun_with_latest_version — added 3.3.0. Controls which Dag version clear/rerun/backfill use; relevant when re-running partition subsets after code changes.

## mwaa: AWS MWAA constraints relevant to a 100k-partition (firm-account fan-out) workload: supported Airflow versions, MWAA Serverless, environment-class limits, config override allow/block list, executor options, large-fan-out guidance, and metadata-DB retention/cleanup.

As of 2026-09-29, provisioned MWAA supports Airflow 3.3.1 (available 2026-09-01), 3.2.1 (2026-05-19), 3.0.6 (2025-10-01), plus 2.11.2/2.11.0/2.10.3/2.10.1/2.9.2/2.8.1/2.7.2; all 3.x images are Python 3.12. There is no 3.1.x and no 3.3.0 on MWAA: the firm's "3.3.0" would run as 3.3.1, and only AWS-built images are allowed (custom images unsupported), so upstream contributions reach MWAA only when AWS ships a new minor (typical lag 3-4 weeks after the Apache release). 2.x->3.x upgrades must pass through 2.11.x; upgrades snapshot/restore the metadata DB, kill running tasks, and can take up to 2 hours.

Provisioned MWAA is CeleryExecutor-only: AIRFLOW__CORE__EXECUTOR is a reserved variable pinned to CeleryExecutor, the SQS broker is service-managed (custom queues disallowed), and AWS's Airflow-3 launch blog lists Edge Executor / remote task isolation as unsupported. KubernetesExecutor, AwsEcsExecutor and AwsBatchExecutor are therefore not options; heavy work can only be offloaded per-task via EcsRunTaskOperator/EksPodOperator/BatchOperator. Hard ceiling: mw1.2xlarge (16 vCPU/48 GB per scheduler and worker; 8 vCPU/64 GB Aurora PostgreSQL), 2-5 schedulers (triggerer co-located; API max 5), workers 1-25 by default (50 via quota increase), webservers 2-5, default celery.worker_autoscale 80,0 on 2xlarge, giving ~2,000 concurrent slots at 25 workers or ~4,000 at 50. core.parallelism defaults to (maxWorkers x slots)/schedulers x 1.5; celery.worker_concurrency is ignored; celery.sync_parallelism defaults to 1 (a single Celery result-sync process) and AWS warns raising it breaks CloudWatch log delivery. In Airflow 3 on MWAA, workers no longer connect to the DB and the Task Execution API server runs inside the webserver (2-5 Fargate containers autoscaled on CPU>70% or ALB connections>15). For 100k task instances that is a new, MWAA-specific choke point with no published sizing guidance.

Config: MWAA translates any section.key to AIRFLOW__SECTION__KEY (key <=64 chars, value <=64 KB), so core.max_map_length, scheduler.max_tis_per_query, scheduler.max_dagruns_*, dag_processor.* and celery.worker_autoscale are settable through the console/API "Airflow configuration options". Only core.multi_team and triggerer.queues_enabled are explicitly blocked (3.2+). A list of variables (executor, broker/result backend, DB URI, parallelism, worker_autoscale, max_active_tasks_per_dag, parsing_processes, broker transport options, statsd) is reserved against startup-script overrides, but the tuning guide still documents parallelism/worker_autoscale/max_active_tasks_per_dag as console-settable. parsing_processes must be <= 2 x vCPU - 1.

Metadata DB: a single-tenant Aurora PostgreSQL cluster (writer + reader metrics published) that customers cannot access, size or tune; the DMS operator explicitly cannot target it; no storage cap is documented ($0.10/GB-month). AWS states MWAA "does not throttle or reject workloads that exceed the environment's capacity" and that unbounded metadata growth degrades scheduler and webserver; its scaling heuristic is DB CPU >65% => scale the class up, not workers out. On v3, cleanup must use `airflow db clean` through the MWAA CLI endpoint (task code cannot import DB sessions); --clean-before-timestamp is required, --tables/--batch-size/--dry-run recommended, and cleaning dag_run cascades to task_instance, task_instance_history, xcom, task_state_store and deadline.

MWAA Serverless (GA 2025-11-17) is a different product: Airflow 3.0.6 image, ECS executor with one Fargate task (1 vCPU/3 GiB) per Airflow task, YAML/dag-factory definitions <=50 KB, Amazon-provider operators plus Python/BashOperator only, no UI or DB access, quotas of 100 workflows, 20 concurrent runs per workflow, 100 per account, 60-minute task timeout, retries <=3; pools, priority_weight, max_active_tis_per_dag(run), trigger_rule, task_group and deferrable are ignored, and dynamic-task-mapping conversion is unsupported. Billing is $0.080 per task-hour (1-second resolution, 1-minute minimum). It cannot host a 100k-partition fan-out.

No AWS doc, blog or re:Post article addresses dynamic task mapping beyond low thousands on MWAA; the only public customer scale figure is LaunchDarkly at 14,000 tasks/day, and they moved execution to ECS because of Celery isolation problems. Community evidence (apache/airflow discussion #36454, Airflow 2.7.3, ~100k mapped TIs) shows scheduler collapse from repeated task_map length lookups and TI x DagRun joins; maintainers (#26172) advise sharding instead of mapping millions. max_map_length (default 1024) is a plain config and raising it is allowed on MWAA, but the practical ceiling is scheduler CPU (16 vCPU max), untunable Aurora (8 vCPU max), the webserver-hosted execution API, celery.sync_parallelism=1, and the 10 TPS default REST-API throttle if partitions are triggered externally.

## asset-partitions-design: Modeling per-firm-account partition STATE in Airflow 3 today (3.3.x, no upstream changes) versus what AIP-76 shipped and what remains on main/3.4

The premise "AIP-76 is a future design" is out of date. AIP-76 is marked Completed (target 3.3.0, page updated 2026-07-15) and shipped in two releases: 3.2.0 (2026-04-07) added `partition_key` columns on `dag_run` and `asset_event` (migration 0095_3_2_0), `CronPartitionTimetable`, `PartitionedAssetTimetable`, one-to-one mappers, and two scheduler tables `asset_partition_dag_run` (APDR) and `partitioned_asset_key_log`; 3.3.0 (2026-07-06) added `PartitionedAtRuntime` + `outlet_events[asset].add_partitions([...])`, `FanOutMapper`/`RollupMapper`/`FixedKeyMapper`+`SegmentWindow`, `wait_policy`, `[scheduler] partition_mapper_max_downstream_keys`, `partition_date`, backfill-by-partition-date, a `clearPartitions` endpoint, and the AIP-103 Task/Asset State Store. 3.3.2 (2026-09-17) is latest; no 3.4.x exists on PyPI. MWAA has offered 3.3.1 since 2026-09-01 (2-5 schedulers, 1-25 workers, arbitrary config overrides except `core.multi_team` and `triggerer.queues_enabled`), so the company's 3.3.0 already has everything below.

(1) Asset model. You do NOT need 100k Assets: one Asset carries `partition_key` per event (<=250 chars, `StringID`). A producer on `PartitionedAtRuntime` calls `add_partitions(list_of_firm_accounts)`; each key becomes its own `AssetEvent`, duplicates collapse, there is no count cap in the SDK. A consumer on `PartitionedAssetTimetable` gets one `DagRun` per key (IdentityMapper default) with `dag_run.partition_key` set, `logical_date=None`, `run_type=asset_triggered`, `run_id` derived from `run_after` (not the key). Events without `partition_key` do not trigger partitioned consumers, and partitioned events do not trigger non-partitioned consumers (fixed 3.2.0, #63848). Consumers cannot filter on `extra` at scheduling time; conditional logic is asset-level (`&`,`|`) plus mappers (`AllowedKeyMapper` allow-list, `FixedKeyMapper`). Per-key state is NOT a first-class table: `asset_event` is an append-only log (no `partition_key` index until 3.4, PR #64610), APDR rows are transient, and "status of firm X" is derived by querying `dag_run` by `partition_key` (3.3 REST supports `partition_key_pattern`, `partition_key_prefix_pattern`, `partition_date_gte/lte`). The 3.3 `asset_state_store` (PK `asset_id` + `key` <=512 chars, value <=65,535 bytes default, no retention, REST list/get/put/delete) is the sanctioned place for per-key cursors/watermarks and can hold 100k keys under one asset.

(2) 100k distinct Assets is a dead end by design, not by hard limit: each would add rows to `asset`, `task_outlet_asset_reference` (PK asset_id,dag_id,task_id), `dag_schedule_asset_reference`, and 100k outlets in every serialized DAG version, with no documented ceiling and no benefit over keys.

(3) The real ceiling is scheduler throughput. `assets/manager.py` writes one `partitioned_asset_key_log` + one APDR per (event, consumer, target key); `scheduler_job_runner.py` drains APDRs FIFO at an internal, non-configurable `MAX_PARTITION_DAG_RUNS_PER_LOOP = 500` per tick with documented head-of-line blocking, then run start is gated by `max_active_runs` (16), `parallelism` (32/scheduler), `max_tis_per_query` (16). 100k keys per cycle therefore means >=200 scheduler ticks just to create QUEUED runs, 100k DagRuns + TIs per cycle, and 300k+ new rows per cycle. The 1000-key fan-out cap applies only to multi-key mappers (FanOutMapper) and is user-overridable. An HA duplicate-run race in the partitioned path (#68045, filed on 3.2.1) has skip-locked claiming in 3.3-stable source but the issue is still open. For comparison Dagster's own docs recommend <=100,000 partitions per asset.

(4) Backfill (AIP-78) is date-range only (`from_date`/`to_date`, `dag_run_conf`, `reprocess_behavior`, `run_on_latest_version`); partitioned backfill (PR #67537, 3.3.0) covers only `CronPartitionTimetable` and returns 422 for `PartitionedAssetTimetable`; segment/categorical keys are explicitly unsupported. "Re-run these 500 accounts" today = loop `POST /dags/{id}/dagRuns` with `partition_key` (or `POST /assets/events` with `partition_key`), or bulk `clearDagRuns` by run_id; `clearPartitions` only resets partition fields.

(5) Recommendation: on 3.3.x model firm-account as `partition_key` on ONE asset, but keep scheduler-visible partitions at ~1k-10k shards (hash bucket or book) and fan accounts inside a shard via dynamic mapping (`max_map_length` 1024) or in-task loops; record per-account watermark/outcome in `asset_state_store`; expose per-account status by querying dag_run/asset_event by key. Contribute upstream: (a) make the 500/tick APDR cap configurable and bulk-insert runs, (b) partition-key-list backfill/re-run (BackfillPostBody has no key field), (c) a durable per-key partition status view, (d) land #70225/#67941 sensors and #68517 `batch_asset_events` (all 3.4), (e) fix #68045, (f) make `partition_mapper_max_downstream_keys` cluster-enforceable.

The hard scale facts for a 30k–100k firm-account fan-out: AIP-76 deliberately makes one partition = one DagRun (N partitions x M mapped tasks = N*M TIs), so "100k partitions" means 100k DagRuns per cycle, not 100k mapped TIs. Three caps stand between you and that: (1) FanOutMapper/any multi-key mapper is capped at 1000 downstream keys per upstream event by default; exceeding it does not truncate, it skips queueing entirely and writes a "partition fan-out exceeded" audit log (verified in 3.3.2 assets/manager.py); the per-mapper override means deployment managers cannot enforce a hard ceiling. (2) The scheduler creates at most MAX_PARTITION_DAG_RUNS_PER_LOOP = 500 partition-driven DagRuns per loop, a hard-coded module constant in 3.3.2 scheduler_job_runner.py, FIFO with documented head-of-line blocking. (3) max_active_runs_per_dag defaults to 16 and applies to partitioned runs, and max_dagruns_per_loop_to_schedule defaults to 20, so 100k queued runs of one DAG would drain slowly and can starve other DAGs (#49508, open, milestone 3.4.0). AIP-76's own design notes say static segment-based partitions should get an artificial limit "similar to dynamic task mapping's 1024". Dynamic task mapping is unchanged in 3.x: max_map_length 1024 with the producing task failing above it; historical evidence shows scheduler collapse in the low thousands of mapped TIs (#29959 fixed batching >4k in 2.7; #45991/#46044 showed 100→500 mapped TIs going 70s→560s on 2.10.4 with TriggerRuleDep quadratic cost, and maintainers said to wait for Airflow 3). The in-flight answer for high-cardinality per-item work is AIP-104 Iterable Tasks / Task Spreading (Draft; PR #62922 in the 3.4.0 milestone with docs tagged versionadded 3.4.0; cited 17k-file benchmark: DTM 3h25m vs async iterable 3m32s), plus AIP-88 lazy expansion (WIP) and AIP-100 scheduler starvation (awaiting review). For comparison Dagster's docs recommend <=100,000 partitions per asset, and the limit there is UI load time, which Airflow's partition UI has not been tested against.

## mapping-internals: Dynamic task mapping internals and hard/soft limits in Airflow 3.x (3.3-stable vs main/3.4), evaluated against a 30k–100k-partition requirement

Airflow 3.x has no hard ceiling on mapped-task count; every limit is soft, and the real constraints are per-row ORM expansion, O(n)-per-pass scheduler work, and the O(n²) runtime XCom pull pattern.

(1) max_map_length. `[core] max_map_length` (default 1024, plain integer, no upper bound) is enforced in exactly one place in both v3-3-stable and main: the Execution API XCom-set route, `conf.getint("core","max_map_length", fallback=1024)`; if the pushing task's `mapped_length` exceeds it the API returns HTTP 400 `unmappable_return_value_length` and the pushing task fails. Because the check runs in the api-server, that is where the override must be set. Literal/parse-time expand inputs (a 100k list built in DAG code) are never checked — `get_total_map_length` just does `len(v)`.

(2) Expansion. In 3.3.x expansion is `TaskMap.expand_mapped_task` (airflow-core/models/taskmap.py); on main it moved to `TaskInstance.expand_mapped_task` and the `task_map` table was folded into `xcom.mapped_length` (PR #73005, merged 2026-09-24, milestone 3.4.0 — schema differs from 3.3.0). Both compute the length from a stored integer (not the payload), then create one `TaskInstance` ORM object per index in a Python `for index in range(...)` loop with `session.add` (3.3's `_revise_map_indexes_if_mapped` does `session.merge` + `flush` per row) inside the scheduler's `_schedule_dag_run` while the DagRun is row-locked. There is no worker-side mini-scheduler in 3.x, so the scheduler's "expansion of last resort" is the only expansion. Every later pass reloads all TIs of the run (`get_task_instances(state=State.task_states)`) and runs `are_dependencies_met` per schedulable TI; TriggerRuleDep filters all finished TIs in Python per TI (its DB count query is memoized per upstream-set per pass). `schedule_tis` then UPDATEs state in chunks of `max_tis_per_query` (default 16), the chunking (PR #30372, 2.7.0) that fixed the Postgres "stack depth limit exceeded" seen above ~4k. Measured data is 2.x only: issue #45991/#46044 (2.10.4) — 100→500 mapped TIs went 70s→560s, 8.5 s per loop, 16 TIs queued per loop; maintainers deferred to Airflow 3 and no targeted fix has landed since. Open 3.x issues: #73311 scheduler crash (DetachedInstanceError in expand_mapped_task, 3.2.1–3.3.1; fix PR #73451 closed unmerged) and #71267 (3.2.0, 500+ mapped tasks + 0.5–2 MB run conf → 5–6x scheduler memory).

(3) Input storage. The mapped list is the upstream's XCom (`xcom.value` JSON / JSONB on Postgres; no Airflow-side byte limit; only DB limits apply). The scheduler never reads the payload. But at runtime each mapped TI of a non-mapped upstream calls `ti.xcom_pull` for the whole list (`PlainXComArg.resolve`, `map_indexes=None`) — 100k TIs each pulling a 100k-element list through the api-server. For a mapped upstream, `LazyXComSequence` issues one API request per item; PR #73790 (draft, 3.4.0) adds `[core] xcom_sequence_chunk_size` (17k items: 17k → ~530 requests).

(4) Nesting. Mapped task groups multiply (`parent_count * current_count`), chained `expand` is linear, `expand_kwargs` accepts mapped output, but docs (3.3.2): "not currently permitted to do task mapping nested inside a mapped task group".

(5) Throughput. A single scheduler enqueues at most `min(max_tis_per_query, parallelism − occupied)` TIs per loop (16/32 defaults); `parallelism` is per scheduler in 3.x; `max_active_tasks_per_dag` 16 per run; `max_active_tis_per_dag`/`max_active_tis_per_dagrun` per operator; `max_dagruns_per_loop_to_schedule` 20.

(7) Scheduler-only benchmark is feasible: `DagRun.schedule_tis` (3.3 and main) sets `not ti.is_schedulable` TIs straight to SUCCESS (duration 0, never queued); `SerializedMappedOperator.inherits_from_empty_operator` returns the serialized `_is_empty` flag, so a mapped EmptyOperator over a literal 100k list exercises expansion + scheduling + DB with no executor and no max_map_length check.

- [core] max_active_tasks_per_dag — default 16; concurrent TIs per dag run (DAG param max_active_tasks); must be raised for wide fan-out
- operator max_active_tis_per_dag / max_active_tis_per_dagrun — per-task concurrency across runs / within one run (added 2.6, PR #29094); enforced in scheduler ConcurrencyMap
- pools — default_pool slots gate the critical section; starved pools skip TIs
- [scheduler] max_dagruns_per_loop_to_schedule — default 20; DagRuns examined and row-locked per loop (higher raised crash likelihood in #73311)
- [scheduler] max_dagruns_to_create_per_loop — default 10
- [scheduler] use_row_level_locking — default True; required for multiple schedulers (SELECT ... FOR UPDATE SKIP LOCKED)
- [scheduler] scheduler_idle_sleep_time / scheduler_heartbeat_sec — loop pacing when idle
- [api] maximum_page_limit (100) / fallback_page_limit (50) — pagination of mapped TI listings in REST/UI
- [core] max_templated_field_length — default 4096; rendered template fields above this are redacted
- [core] xcom_sequence_chunk_size — default 32; only in draft PR #73790 (3.4.0), not in 3.3.x
- [core] task_success_overtime — default 20 s; time for post-success auxiliary work (listeners) — note: no worker-side mini scheduler exists in 3.x

## prior-art: Prior art — how big Airflow shops handle very high fan-out / entity-level partitioning, and community scale benchmarks (Airflow 2.x vs 3.0–3.3, MWAA)

Prior art falls into three families, and none of them runs 100k task instances inside one DAG run on stock Airflow.

(1) Mapped-task fan-out in one run. Evidence is consistently negative above a few thousand indices. [core] max_map_length defaults to 1024 and the 3.3.0 config text says it exists "to prevent the mapped tasks from clogging the scheduler"; the 3.3.2 docs give no other numeric guidance and forbid expand nested inside a mapped task group. Issue #29959 / discussion #28478 (Airflow 2.4–2.5): raising the cap past ~4k froze the scheduler and hit Postgres "stack depth limit exceeded". PR #30372 (2.7.0) batched the status UPDATEs and cut 10k-mapped expansion from 7–10 min to seconds, but the scheduling loop stayed the bottleneck: issue #45991 (2.10.4, Jan 2025) measured 100 mapped → ~70 s and 500 mapped → ~560 s (effective parallelism 9 → 5), an ~8.5 s loop spent in are_dependencies_met with only max_tis_per_query=16 TIs queued per loop; potiuk declined to fix it in 2.x. The most authoritative statement of the 100k goal is Jens Scheffler (Bosch, PMC) on AIP-100, Jan 25 2026: scheduler slowness "mainly limits us from mapped tasks >1024. We would like to have 100k mapped possibilities" — their workaround is child DAG runs, "a mess in terms of usability". AIP-100 (created 2025-12-29, AWAITING COMMUNITY REVIEW as of May 2026) is the upstream vehicle: it blames the critical section's optimistic fetch + Python filtering and weighs window functions (PR 53492, poor SQL perf), stored procedures (PR 55537) and DAG-level priority semantics; issue #45636 is milestoned 3.4.0. Jens' Aug 2025 dev-list thread defines "very large DAGs" as 10k–100k tasks and calls for a 10K–1M-tasks-per-DAG initiative. Still open in 3.3.1: #73311, a scheduler crash in TaskMap.expand_mapped_task with 10+ concurrent mapped runs.

(2) One DAG run per entity. This is what big shops actually run. Bosch (Summit 2024, Airflow 2.6–2.8): 1 event = 1 one-task DAG run, peak 1,295,023 runs/24h, 50k/h sustained, 70k/h peak, ~1 s per run, on 3 schedulers, 15 Celery workers ×16, Postgres 8c/32GB + PgBouncer, parallelism=500, max_dagruns_per_loop_to_schedule=200, max_active_runs/tasks 360, six scheduler patches upstreamed, and a custom 7-day archiver because 40M dag_run rows broke VACUUM. Airflow 3 makes this cleaner (AIP-83: logical_date nullable, uniqueness dropped, explicitly "for folks who generate many dag runs in quick succession via API"). Caveats: issue #54283 (3.0.3) shows loop time growing to 15 s after 100k completed runs / 3M TIs in 12 h (closed not-planned; 3.2.0 later stopped loading all TIs in memory), and #56646 (max_active_runs ignored) is open.

(3) Asset partitions (AIP-76, 3.2.0/3.3.0) are Airflow's Dagster analogue and are explicitly "N DAG runs in parallel, not a DAG run with N executions". FanOutMapper is capped by partition_mapper_max_downstream_keys=1000 and creates zero runs when exceeded (audit-log entry only). AIP-76 itself says static segment partitions need "an artificial limit" like DTM's 1024. Datadog is the marquee adopter.

Everything else at 100k+ is sharding or pushing fan-out down: OpenAI sharded clusters when one metadata DB choked at "thousands of concurrent tasks"; Capital One runs hundreds of isolated instances; Shopify's lesson is that scheduler throughput cannot be partitioned per workload without isolated environments; potiuk's canonical answer to million-item fan-out is "Airflow orchestrates chunks, Spark processes items"; Step Functions Distributed Map defaults to 10k concurrent children with ItemBatcher. Uber (200k pipelines, ~800k TIs/day) is consolidating onto one Airflow 3 instance, but via plugins and new AIPs. Public throughput data is thin: Astronomer 2020 (1,000 tasks, 1.10→2.0 gives 10–17× lower latency), Google's Summit 2025 test (10 DAGs × up to 10k no-op tasks, 3.0.0 vs 2.10.5: AF3 faster, 2 schedulers help, a 3rd does not, worker scaling linear 3→6) and Astro's proprietary executor (228 ms p95 at 100k concurrent). None exercises a 50k–100k-TI single run. MWAA (3.3.1 available since 2026-09-01) caps at 5 schedulers, 25 workers, 80 slots/worker (2,000 slots) and does not support multi-team.

## Completeness critic

# Completeness critique: Airflow at 100k firm-account partitions

## (a) Important sub-questions nobody answered

1. **Balance-sheet team is invisible.** The platform is shared, but no researcher analyzed noisy-neighbor effects: 100k QUEUED revenue runs vs. BS DAGs under #49508/#45636 starvation, single default pool (128 slots), and MWAA blocking `multi_team`. Isolation strategy (separate MWAA env vs pools/priority_weight) is the real platform decision.
2. **What is the per-account unit of work?** Duration, data size, idempotency, and whether accounts are independent decide everything (100k runs vs 1k shards × 100 in-task loops vs AIP-104 iterate). Nobody asked.
3. **End-to-end drain time was never computed.** Everyone fixated on the 500/tick creation cap (≥200 ticks ≈ 3–4 min). The binding constraint is `max_active_runs_per_dag` × per-run scheduler latency: at 16 active runs and ~5–10 s per single-task run, 100k runs ≈ 9–17 hours. Raising to 2k active runs is untested (#56646 says the knob is sometimes ignored).
4. **Metadata retention on MWAA**: 100k `dag_run` + ~300k asset/APDR rows per cycle; `asset_partition_dag_run` rows are never deleted (verification); `db clean` is CLI-only on MWAA. No retention plan or daily-row budget.
5. **Version reconciliation**: "company runs 3.3.0" but MWAA only has 3.3.1, and several cited features (partition_date filters, alias TypeError, asset-event maxLength) are 3.3.1+. Is 3.3.0 self-hosted?
6. **Contribution timeline**: 3.4.0 feature-freezes 2026-10-05 (6 days away). Anything new lands in 3.5 (~Q1 2027) and reaches MWAA 3–4 weeks later. Nobody stated this.
7. **External triggering math**: MWAA REST throttle 10 TPS → 100k `POST dagRuns` ≥ 2.8 h. Kills the "re-run 500 accounts via API loop" fallback at scale.

## (b) Contradictions across researchers

- **Upstream 3.3.x defaults**: the MWAA researcher lists `max_dagruns_per_loop_to_schedule=10`, `max_tis_per_query=0`, `task_queued_timeout=1800`, `sql_alchemy_pool_size=0`, `min_file_process_interval=0`; four others say 20/16/600/5/30. One side read the wrong config version. Confirm against `config.yml` at tag 3.3.2 before tuning.
- **Bosch analogy**: prior-art says "one run per event, 50k/h sustained"; verification says one run per **64-event batch**, 5–10k/h actual. This flips the lesson toward batching.
- **#45991 units**: cited as 100/500 mapped *tasks*; verification says 100/500 mapped *task groups* = ~400/2000 TIs. Extrapolations to 100k are off by 4×.
- **`max_dagruns_to_create_per_loop` throttles partition runs** (releases) vs. does not (verification).
- **APDR "transient"** vs. "never deleted."
- **Expansion cost on main**: mapping-internals says merge-per-row everywhere; verification says #69565 (single flush) is on main but not in 3.3.1/3.3.2 despite its milestone. Benchmark must compare both.
- **Fan-out cap skip scope**: whole event vs. per-target DAG.

## (c) Suspicious numbers

- **"≥200 ticks"** is a lower bound on creation only, not on completion (see a-3).
- **AIP-104 17k-file 60× speedup**: SFTP-I/O-bound PR-author benchmark; says nothing about scheduler cost.
- **Astro Executor 228 ms p95 at 100k**: proprietary vendor claim, not Celery/MWAA-transferable.
- **#69848 290 MB at 50k asset events**: main branch, non-partitioned path; assumes linear extrapolation to partitioned 100k.
- **MWAA "2,000 slots"**: Celery slots; `parallelism` formula, `sync_parallelism=1`, and 16-vCPU scheduler almost certainly bind first.
- **Dagster 250k Dagster+**: one support-engineer comment, undocumented.
- **Google Summit "3rd scheduler no gain"**: medium confidence, garbled PDF.

## (d) Five things the laptop benchmark must measure

(8 GB RAM caps realistic concurrency at hundreds; measure *curves*, not absolutes. Run each on 3.3.2 and main.)

1. **Partition-run drain**: `PartitionedAtRuntime` producer with `add_partitions(N)`, N ∈ {1k, 10k, 100k}; consumer = single EmptyOperator. Record: ticks to all-QUEUED, wall time to all-SUCCESS at `max_active_runs` ∈ {16, 256, 2048}, per-loop time, scheduler RSS peak. This settles whether 500/tick, `max_active_runs`, or per-run overhead binds.
2. **Mapped expansion/scheduling curve**: mapped EmptyOperator over literal list N ∈ {1k, 5k, 20k, 100k} (no `max_map_length` check, no executor needed), plus the #45991 shape (mapped groups of 4). py-spy the scheduler for `are_dependencies_met` share; log TIs queued per pass. Also try >10 concurrent mapped runs to reproduce #73311.
3. **Row growth and query cost**: rows/cycle in `dag_run`, `task_instance`, `asset_event`, `asset_partition_dag_run`, `partitioned_asset_key_log`; `dag_run WHERE partition_key=` latency at 1M rows (unindexed in 3.3); `airflow db clean` duration and whether APDR/PAKL are cleaned.
4. **Static key sets and cap override**: `FanOutMapper(max_downstream_keys=100_000)` and `FixedKeyMapper`/`SegmentWindow` with 30k keys: serialized `partition_mapper_info` size, DAG parse time, per-event evaluation time, all-or-nothing skip behavior.
5. **Hybrid shard baseline**: 1k shards × 100 accounts (in-task loop or `expand` ≤1024) vs. 100k runs — total time, rows written, and Execution API request count per TI (full-list XCom pull of a 100k-element list is the hidden cost).

## (e) Three things that cannot be settled locally

1. **MWAA ceilings**: pass-through of `core.max_map_length`, `scheduler.max_tis_per_query`, `core.max_active_runs_per_dag`; Aurora 8 vCPU behavior; webserver-hosted Execution API throughput; `celery.sync_parallelism=1`. *Settle*: mw1.large→2xlarge trial on 3.3.1, replay benchmark (d1) at 10k, watch DB CPU/scheduler heartbeat/webserver CPU in CloudWatch; open a Support case for worker/scheduler/DB quotas and 3.3.2 image cadence.
2. **Multi-scheduler + multi-team behavior**: skip-locked APDR claiming (#68045), critical-section contention (AIP-100), BS-vs-revenue starvation. *Settle*: 3-scheduler Celery+Postgres+PgBouncer cluster (Helm or docker-compose) mirroring MWAA, run both teams' DAGs concurrently.
3. **Upstream acceptance**: configurable/non-FIFO APDR draining, key-list backfill, "partition set" run type, AIP-104/AIP-100 fate. *Settle*: post benchmark data from (d) to dev@airflow and the AIP-100/#46044 threads before the 3.4.0 freeze; ask maintainers directly whether they want one-run-per-key to scale or prefer batching.
